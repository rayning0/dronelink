What makes a live video call different from streaming TV? Low delay (or latency) and fast two-way communication. Video calls, police/fire rescue, telehealth, the military, etc. all use WebRTC (Web Real-Time Communication).

[Show webrtc_latency.png]

That matters for drones. At 40 mph, a drone flies 30 feet in half a second. It could crash with slower communication. Last weekend, I built DroneLink in 2 days: a low-latency RemoteOps simulator in Go, JavaScript, LiveKit, and WebRTC.

[Show live video in 2 browser tabs.]

On the left is the simulated drone camera: my webcam stands in for an onboard camera. On the right is the operator console, getting live video through LiveKit.

[Show mermaid_dronekit_simple.png]

LiveKit is an SFU, or Selective Forwarding Unit, a smart traffic director. The drone uploads 1 video stream to LiveKit, which can forward it to an operator or other authorized viewers. The operator sends control commands back. The drone does not upload the same video separately to everyone.

[Show Arm, Take Off, brief movement, telemetry, and animated drone visuals.]

The operator can arm, take off, move, land, and return home. The animated drones are a simulation that makes control visible; the webcam video is real WebRTC. The Go agent returns state, altitude, battery, velocity, and command telemetry.

[Show Return Home. Speed up the long hold after landing.]

Here is Return Home. The top-view drone returns home, then the side-view drone lands. Cool, huh?

What if the operator suddenly loses connection to the drone while it's still moving? It should stop moving, so it won't crash. This is a safety feature called the dead-man failsafe.

[Demonstrate dead-man failsafe: move with W, click Leave, rejoin and show HOVER_FAILSAFE.]

If the drone is moving and fresh movement updates stop for 500 ms, the Go agent stops in mid-air (0 velocity) and hovers in "HOVER_FAILSAFE" state.

[Show WebRTC Link Health.]

The console reads real browser WebRTC statistics: delay, packet loss, jitter, bitrate, and whether the path is direct or relayed. This local demo has excellent numbers; in production, these help diagnose poor connections.

[Show Mermaid architecture diagram.]

The design separates the media plane from the control path. LiveKit routes video to the operator. The Go drone agent validates commands and returns telemetry. Its simulated-drone boundary could later become a MAVLink adapter for a real flight controller.

[Technical appendix: show main.go /token handler, drone-agent/main.go, main_test.go, and operator.js.]

For engineers: the Go token service issues short-lived, role-scoped tokens. The drone agent uses a mutex-protected state machine: DISARMED, ARMED, FLYING, LANDING, and HOVER_FAILSAFE. It validates timestamps, rejects stale velocity updates, and handles duplicate command IDs safely.

I added unit tests for invalid takeoff, stale, duplicate, and out-of-order commands, the dead-man timeout, and safe landing. operator.js connects the console, displays video and telemetry, sends controls, and reads WebRTC stats.

DroneLink is a small prototype, but it shows low-latency media, SFU routing, WebRTC, Go state machines, observability, and failure-safe behavior. Thank you for watching.
